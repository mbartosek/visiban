# Service Layer

Board mutations that carry invariants live in `backend/boards/services/`, not in the DRF views that expose them over HTTP.

## Why the layer exists

Until Visiban 1.2 every card state transition was implemented inline in `CardViewSet`. That was fine while the REST API was the only writer. It stopped being fine as soon as a second consumer appeared, because an invariant that lives inside an HTTP handler can only be reached by making an HTTP request — so any second code path has to either re-implement the rules or skip them.

Both failure modes had already happened:

- The MCP tool scaffold carried its own copy of the board-role precedence ladder, with a comment saying it "must be kept in step with" the original. Nothing enforced that.
- A `PATCH` that changed a card's `column` bypassed WIP enforcement and the movement audit trail entirely, because only the move endpoint evaluated them.

The API now has several writers in view — a second front end, MCP write tools, import, and webhooks — so the invariants need a home that is not a request handler.

## What a service function owns

For one state transition:

| Concern | Example |
|---|---|
| Role allow-list | only `member`, `admin`, `site_admin` may mutate a card |
| Ownership / assignment gate | a member may edit only cards they created, unless they hold the moderator entitlement |
| Optimistic concurrency | compare the caller's `version` against the stored row |
| Row locks, in a fixed order | the moved card plus every card in its source and target cells, in one statement ordered by pk → the source and target column rows, in one statement ordered by pk (`FOR NO KEY UPDATE`, on every move; a same-cell reorder locks its one column) |
| Limit enforcement | WIP soft, WIP hard, weight, and the `force` override authorization — one helper, `enforce_column_limits()`, shared by move, create, restore, and a weight increase on update (#1428) |
| Audit trail | the `CardMovement` row and the `CardActivity` diff |
| The transaction | one `atomic()` block per transition |
| Deferred side effects | the `transaction.on_commit()` WebSocket broadcast and `CARD_MUTATION_HOOKS` |

The lock order is a deadlock-avoidance contract, not an implementation detail: concurrent moves queue behind each other only because every caller takes the same locks in the same sequence. Two consequences of #1522 are easy to undo by accident. First, card rows are never locked one statement at a time: locking the moved card and then its siblings deadlocked two moves out of one cell, because each held its own card and wanted the other's. Because the source cell is only known after the card is read, `move_card` reads it unlocked, locks the cells, and re-checks the card under the lock, retrying if a concurrent writer changed it (and returning `409` if that keeps happening). Second, column rows are locked after the card rows, source and target together in one pk-ordered statement, before the `CardMovement` insert takes key-share locks on both columns. A column reorder holds `FOR UPDATE` on every column (`position` is part of a unique key) and locks them in the same pk order. A move that locked only its target column deadlocked against a reorder. The column lock mode is `FOR NO KEY UPDATE` so that it does not block the key-share locks unrelated inserts take on the column (a card created in it, say). Under the current order a plain `FOR UPDATE` would not make two moves deadlock; the mode is pinned only by `test_move_locks_cards_then_columns_in_pk_order`. Third, the card-row lock statement locks the rows of the snapshot it took before it waited, so a card that a concurrent move commits into one of the cells during that wait is not locked by it; the later compaction or shift `UPDATE` would then lock it outside pk order, and a third move could deadlock against it (#1567). So once `move_card` holds the column rows, which every service path that puts a card into a cell (`create_card`, `move_card` and the tools that call them) also takes, it re-reads its cells' members (`_require_cells_locked`) and retries if any is unlocked. Django admin card edits follow the same card-then-column order (#1588): `CardAdminForm.clean` locks the card row and re-reads it, then locks the source and target columns in one pk-ordered statement whenever the card's column or swimlane changes (archived cards included) or a WIP/weight check runs, and the check counts under that lock. For that reason the column lock is taken on every move, including a reorder within one cell. `create_card` against a column reorder (#1566) is fixed by taking the reorder's board-row lock `FOR NO KEY UPDATE`: the card insert's foreign-key check needs `FOR KEY SHARE` on the board row at commit, which a `FOR UPDATE` board lock blocks while the reorder waits on the column the create holds.

Deleting a user from the Django admin (#1616) takes its locks in the order user, card, user. Statement 1 locks the targets, the acting administrator and the active site-admin and superuser rows `FOR NO KEY UPDATE`, which does not block the `FOR KEY SHARE` that card writes and board inserts take on a user row. Statement 2 locks the owned boards' rows `FOR NO KEY UPDATE`, then the cards the cascade will write (the owned boards' cards and every card carrying a reference to a target) with `FOR UPDATE`, then the owned boards' entry columns (`lock_cards_for_cascade()` with `boards=` and `entry_columns=`, #1602), so the board -> card -> column order matches every other container delete, and statement 3 locks the target rows `FOR UPDATE` and judges the refusals again, so a board committed by then is seen and the delete is refused. The card set is a snapshot taken at statement 2, like the snapshot in #1567 above, and that is a stated limit: a card that gains a reference to a target between statements 2 and 3 is not locked, so the cascade's `SET NULL` update of it runs while the delete holds the user row `FOR UPDATE`, and a writer holding that card, which needs `FOR KEY SHARE` on the user at commit, can deadlock with it. PostgreSQL aborts one side, which can be the delete; no data is lost. Tables not scoped to a card are not locked.

Writes to an existing card also hold that card's row against a concurrent hard delete (#1587). `update_card`, `archive_card`, `unarchive_card` (before its column limit check), and the card-child writes in `CardViewSet` (comment, checklist item, and attachment create; checklist item edit and delete, which write an activity row) call `lock_card_for_write()` first in their transaction: it locks the card row `FOR NO KEY UPDATE` and raises `CardNotFound` (a `404`) if the row is already gone. Relation create gets the same answer from its existing pk-ordered lock on both cards. `delete_card` locks the row `FOR UPDATE` before Django collects its cascade, and re-checks `archived_at` under that lock so a card archived concurrently is still refused. Without these locks, a delete committing mid-write either let `update_card`'s `save()` fall back to an `INSERT` that re-created the deleted card, made an archive or restore's `save(update_fields=...)` match no row (a `500`), or failed the child insert's deferred foreign-key check at commit with a `500`. The lock is a card row, so it goes before any column row the same transaction locks. `lock_card_for_write()` returns the row it locked, and `update_card` copies it onto the caller's pre-lock instance before `apply()` (#1598): `serializer.save()` writes every column of that instance, so without the re-read an archive or move committed between the caller's read and the lock was written back over — `archived_at` cleared and the card returned to its old cell with no `CardMovement` row. The archived guard and the `use_move_endpoint` cell check are re-run on the locked state. `archive_card` and `unarchive_card` do the same (#1605): they re-check `archived_at` on the locked row, so a card archived (or restored) by a concurrent request in that window gets the existing no-op answer — `200` with the card, and no second `CardMovement` row, broadcast, or hook — and the `ARCHIVED`/`UNARCHIVED` movement row and the restore's column limit check use the card's cell as it is under the lock, not the cell a concurrent move took it out of. Both also read the set of cards the card blocks under that lock, as `delete_card` does, so a `blocks` relation created while they waited still gets its peer a `card.updated` frame (relation create locks both cards, which conflicts with the card lock).

The response render is a delete race too (#1585). The view's render callbacks for `move_card`, `archive_card` and `unarchive_card` raise `CardNotFound` (`404`) when the card is gone by the time they re-read it, rather than leaking `Card.DoesNotExist` as a `500`. Inside the service's transaction that rolls the write back with no broadcast; for the renders that run after `archive_card`'s transaction (and the `unarchive_card` no-op) the write is already committed and the answer is still `404`, because a `200` would have to invent a payload for a card that no longer exists. The Django admin's card-child hooks (comment and checklist) cannot surface a DRF `NotFound`, so they differ: `save_model` takes `lock_card_for_write()` on the parent card before inserting the row (as the REST endpoints do, #1587) and answers a Django `Http404` if the card is already gone, so a card delete can no longer fail the deferred foreign-key check at commit with a `500`; the delete hooks look the card up by id rather than through the lazy `obj.card`, and skip the `card.updated` broadcast for a vanished card. `delete_queryset` refetches every card before recording any event, so a card vanishing part-way cannot leave a partial broadcast. `CardAdmin.save_model` likewise skips the broadcast for a vanished card.

Deleting a column, swimlane, or board cascades to its cards, and has the same race (#1599). `ColumnViewSet`, `SwimlaneViewSet`, and `BoardViewSet` call `lock_cards_for_cascade()` first in their delete transaction. It locks every card the delete will cascade to, archived ones included, `FOR UPDATE` in one statement ordered by pk, before Django collects the cascade. A child write that already holds a card lock commits first, so the cascade sees its new rows and removes them. A child write that arrives later waits, finds the card gone, and answers `404`. Without the lock, the container delete failed its own deferred foreign-key check at commit with a `500`. The card rows are locked before the container row, and in pk order, like `move_card`'s card lock, so the two queue rather than deadlock. The statement locks with `FOR UPDATE OF` the card table only, so a filter that joins (the user admin's `board__owner`) does not also lock board rows.

The card statement locks the rows of its snapshot, so on its own it did not cover a card that entered the container after it ran (#1602): a card `create_card` inserted into the container, or one `move_card` moved into an empty cell of it (no container card to wait on), could commit before the collector's card `DELETE`, and the delete then failed the same deferred foreign-key check at commit with a `500`. The other order was a `500` too: a create that queued behind the delete found its column gone (`Column.DoesNotExist`), and a create or move into a deleted swimlane failed its own deferred check. Locking the container row before the cards would close it but inverts the card -> column order above, so the fix keeps that order and reuses the guarantee `move_card`'s re-check (#1567) rests on: every path that puts a card into a cell (`create_card`, `move_card` and the tools that call them, and the Django admin card form through `lock_card_cell_entry`, #1588) holds that cell's column row `FOR NO KEY UPDATE` until it commits. The destroy paths therefore pass `lock_cards_for_cascade(cards, entry_columns=..., boards=...)` the column rows a card can enter through (the deleted column itself, or every column of the board for a swimlane or board delete) and the board row(s). After the cards, the helper locks those columns in one pk-ordered `FOR NO KEY UPDATE` statement, the same mode and order as `move_card`'s column lock. Once it holds them no card can enter the container, and any card that entered before has committed, so the helper re-reads the container's cards. If one is not among the rows it locked, it rolls back to a savepoint, which releases that attempt's row locks, and repeats. It does not lock the newcomer in a second statement: that would take a card row after a column row, and could deadlock with a move of that card that holds it and waits on the column. A container that gains a card on every one of three attempts raises `ContainerChanged`, which the REST views answer with `409` (`code: container_changed`) and nothing deleted. On the entry side, `create_card` and `move_card` re-check their target column (from the locked rows) and swimlane once they hold the column row, and answer `404` (`ColumnNotFound` / `SwimlaneNotFound`) for a container deleted while they waited; the Django admin card form makes the same checks and refuses the save with a form error. `move_card` re-reads the swimlane only when the card changes swimlane: a container the card is already in has to lock the card first, so the card lock already answers that case.

Holding the entry columns needs the board row taken first. Column create, swimlane create and swimlane reorder lock the board row `FOR UPDATE`, and column reorder locks it `FOR NO KEY UPDATE` (#1566), each *before* any column or swimlane row. A board delete that held the board's columns and only reached the board row at its final `DELETE` therefore deadlocked against a column reorder that held the board row and waited on a column (the shape #1604 describes, which the early column lock made easy to hit). So every container delete — the REST column, swimlane and board views and the column, swimlane, board and user admins — locks its board row(s) first, pk-ordered, `FOR NO KEY UPDATE`, before the cards. That mode conflicts with every board-row lock above, so a structure write and a container delete on one board queue whole, in either order, in the same board -> column order. It does not conflict with the `FOR KEY SHARE` a card insert takes on the board at commit; `FOR UPDATE` would, and a `create_card` holding a column would then wait on the board while the delete waits on that column. A request that queued behind a board delete finds the board gone and answers `404` through `lock_board_row_or_404`, which every board-row lock site in the views uses: column and swimlane create and reorder, card and swimlane custom-field definition create, label create, saved-filter create, star, member add and removal, the invite caps (shareable link create and emailed invite send), and the invite join (#1631). The invite-only registration path takes the same board lock through `boards.invites.lock_invite_board` instead and answers `invite_invalid` rather than `404`; definition update and delete, label update and delete, and column and swimlane update take the board row `FOR NO KEY UPDATE` and then their own row through `lock_board_and_row_or_404`. The Django column admin raises `Http404` instead. The board lock also closes the case where a column is created mid-delete: the REST column create and the Django column admin (on add and on edit) take the board row first, so no column can appear in, or be re-pointed at, the board after the delete's column statement, and `entry_columns` covers every column a card can enter through. No path takes a board-row lock after a card or column lock in the same transaction. The full order:

| Transaction | Lock order |
|---|---|
| Container delete (column, swimlane, board; REST and admin; user admin for owned boards) | board row(s) `FOR NO KEY UPDATE` -> container's cards `FOR UPDATE` (one pk-ordered statement) -> entry column rows `FOR NO KEY UPDATE` (one pk-ordered statement) -> the collector's `DELETE`s |
| Card entry (`create_card`, `move_card`, admin card form) | moved card and cell cards (one pk-ordered statement) -> source and target column rows (one pk-ordered statement); `FOR KEY SHARE` on the board, column and swimlane only at commit |
| Card write and card delete | card row -> any column row |
| Column reorder | board row `FOR NO KEY UPDATE` -> every column row `FOR UPDATE` (pk order) |
| Column or swimlane create, swimlane reorder, custom-field definition create, invite caps | board row `FOR UPDATE` -> its own rows |
| Invite redemption (join view; invite-only registration, REST and OAuth) (#1631) | board row `FOR NO KEY UPDATE` (`lock_board_row_or_404` / `lock_invite_board`) -> invite row `FOR UPDATE` (or the registration claim's conditional `used_at` `UPDATE`) -> membership and redemption inserts |
| Board, column, swimlane, label and custom-field-definition UPDATE/DELETE writers (custom-field definition update and delete included, `FOR NO KEY UPDATE` through `lock_board_and_row_or_404`, not `FOR UPDATE`): board `PATCH`/`PUT`, share link enable/revoke, move-group, member add/role change/removal, label create, saved-filter create and star (board row only), column `PATCH`/`PUT`, swimlane `PATCH`/`PUT` and set-collapsed, label `PATCH`/`DELETE`, card and swimlane custom-field definition `PATCH`/`DELETE`; `BoardAdmin`, `ColumnAdmin`, `SwimlaneAdmin` (and the label and membership admins) saves | board row `FOR NO KEY UPDATE` -> (column, swimlane, label or definition writers) that row `FOR NO KEY UPDATE` -> the `UPDATE`/`DELETE` |

No path may lock a board row after it holds a board invite row in the same transaction: the board delete holds the board row and reaches the invite at its collector `DELETE`, so that order would deadlock against it. Invite revokes hold only the invite row and take no board lock (`BoardEvent.board_id` is a plain integer, not a foreign key).

The card admin delete takes no board or column lock: a card delete has no container a card can enter.

Writers that `UPDATE` a board, column or swimlane row need the board row too (#1602). Because a container delete holds the board row from its start, a writer that went straight to its `UPDATE` queued behind the whole cascade (the board `UPDATE` takes `FOR NO KEY UPDATE` on the board row itself, a column `UPDATE` on a column row the delete holds) and then found its row gone: `serializer.save()` and a full `save()` fall back to an `INSERT` when the `UPDATE` matches no row, which re-created the deleted board with no columns or members, or tripped an `IntegrityError` the column view reported as a misleading `400`; `save(update_fields=...)` raised instead (a `500`). Each writer now takes the board row (`lock_board_row_or_404(board, no_key=True)`), and a column or swimlane writer then its own row (`lock_board_and_row_or_404`), before saving, so a writer queued behind a delete answers `404` (the admin raises `Http404`, through `_lock_board_for_admin_save`) and writes nothing. `FOR NO KEY UPDATE` is the mode the `UPDATE` takes anyway, so it adds no new conflict, and it does not block a card insert's `FOR KEY SHARE`. Move-group now saves with `update_fields`. Label create, saved-filter create and star take the board row (`FOR NO KEY UPDATE`), so they queue with a board delete in both orders: a row committed between the delete's cascade read and its `DELETE` would otherwise fail the delete's deferred foreign key at commit, and a label created after the delete reported a misleading `400`. A column, swimlane or board `DELETE` that queued behind another delete of the same object re-checks, once it holds the locks, that the board and the object still exist and answers `404` without storing or broadcasting a second deletion event (`require_present_or_404`). The column, swimlane, label and custom-field-definition `PATCH`/`PUT` reload the row under the lock before saving, like the board `PATCH`. Label and custom-field-definition writers take the same two locks (`lock_board_and_row_or_404` with the label or definition model): their `PATCH`, queued behind a `DELETE` of the same row, updated no row and `save()` inserted it again under the same pk, re-creating the deleted label or definition; the `DELETE` takes the locks too, so a second delete or a delete after an update answers `404` rather than broadcasting twice. Member add and role change (`members`) and member removal (`remove_member`) take the board row, so they queue with each other and with a board delete and answer `404` once the board is gone, not a `500` from the deferred board foreign key at commit; a role change queued behind a removal re-creates the membership as a new add, which is the result of the two in sequence. The board `PATCH` reloads the board under the lock before saving, because `save()` writes every column and the snapshot read before the lock could overwrite fields another request changed (the share link fields, the group) while the `PATCH` queued, so the `PATCH` now applies only the fields the request sent; `move_group` reads the group the board is leaving from the locked row, so the `board.deleted` event reaches the group it actually left. `lock_board_and_row_or_404` also scopes the row to the board, so a pk from another board is `404`. The other writers of board-owned rows are left as they were because they cannot re-create a deleted board, column or swimlane: custom-field-definition, swimlane-custom-field-definition, column and swimlane reorders use `bulk_update`, which matches nothing once the rows are gone; the user-admin board transfer is a queryset `update()` (same); the board saved in group board create is created in that request; and the invite link revoke already locks its row (`select_for_update`) and answers `404` once it is gone. Group membership role edits are not board-scoped and are not covered here. Invite redemption (#1631) — the join view and invite-only registration, REST and OAuth — takes the board row `FOR NO KEY UPDATE` (`lock_board_row_or_404` in the join view, `lock_invite_board` on the registration path) before it locks the invite row, reading the invite's board id unlocked first: a redemption that held only the invite row and inserted the membership and redemption rows under it made a board delete, waiting on that invite at its collector `DELETE`, fail its deferred foreign keys at commit, and locking the board after the invite would deadlock against it. A redemption queued behind a board delete answers `404` (join) or `invite_invalid` (registration) with nothing written or broadcast; the consume-once claim is unchanged, still taken under the invite row lock (or the conditional `used_at` update). Tracked separately as #1638: a group invite join racing a group delete, which this change does not cover. A card `PATCH`/create that names labels or custom-field definitions locks those rows (`FOR NO KEY UPDATE`, in pk order, after the card row) and re-resolves them under the lock (#1632): the label or definition `DELETE` takes the same lock first, so it queues behind the card write and cascades the rows written, and a card write that lost the race answers `400` (as a request naming an unknown id always did) instead of a `500` from the deferred foreign key at commit. The swimlane `PATCH` route re-checks its definitions after taking the board row (an unknown definition answers `400`, as a `PATCH` naming one always did), because this change made it queue with definition deletes. The seed commands' `--wipe` (`seed_demo_data`, `seed_template_boards`) delete through `delete_boards_locked`, which takes the same locks as the board destroy view, because the demo cronjob runs them against a live instance. The helper resolves the board set to pks once, inside its transaction, and uses those pks for every lock statement and the final `DELETE`, so a board created with the same name between statements cannot be deleted unlocked.

The Django admin delete paths take the same lock (#1603): the card, column, swimlane, and board admins, and the user admin (a user delete cascades to the boards they own and those boards' cards). Each `delete_model` and `delete_queryset` runs `lock_cards_for_cascade()` and the delete inside one `transaction.atomic()`. The outer transaction matters for bulk admin actions, which Django does not wrap, so a lock taken per object would be released before the delete. The column, swimlane, board and user admins also pass `entry_columns` and `boards` (#1602), so a card created in, or moved into, the container mid-delete is covered, and the board row is taken first, as on the REST paths. The card admin passes neither: a card delete has no container a card can enter. The rare `ContainerChanged` after three lost attempts is caught at the view level (`ContainerChangedAdminMixin`), not in `delete_model` or `delete_queryset`, because Django prints its success message after those return: a single delete shows the error and returns to the object's change page, and a bulk `delete_selected` runs in one transaction, so the deletion log entries Django writes before `delete_queryset` roll back too, and returns to the changelist with the error. Nothing is deleted in either case.

## What stays in the view

Nothing under `boards/services/` imports `rest_framework`, reads a request, or builds a response. The view adapter keeps:

- **Parsing**, mostly. `?force` becomes a `bool`. The exception is `version`, which the adapter passes through raw: *when* the "version must be an integer" `400` is raised is part of the frozen contract — it comes after the role allow-list, the card lookup, and the assignment gate — so the coercion lives in the service. Parsing it in the adapter turns a `403` into a `400` for a caller who sent both a bad version and a request they were not allowed to make.
- **Field validation.** Per the project rule that input is validated at the serializer boundary, `create_card` and `update_card` take a callable that performs the already-validated write — `serializer.save()` for the HTTP adapter. `CardSerializer`'s querysets are board-scoped, so a cross-board column, swimlane, label, or assignee id is already a `400` before the service is reached.
- **Serialization.** Each function takes a `render` callable and invokes it *inside* the transaction, because the REST response body and the WebSocket payload are deliberately the same dict. Re-serializing in the adapter after commit would cost a second multi-query fetch and would let a concurrent writer land between the write and the read.

That last point is the one place the boundary is a compromise rather than a clean cut, and it is deliberate: the service stays serializer-agnostic, and the adapter decides what a payload looks like.

## Errors

`boards/services/errors.py` holds one class per failure mode, each carrying the exact HTTP status and response body its endpoint returned before the extraction. A view adapter is therefore a single clause:

```python
def handle_exception(self, exc):
    if isinstance(exc, CardServiceError):
        return Response(exc.body(), status=exc.status)
    return super().handle_exception(exc)
```

The bodies live in that module, rather than being reassembled in the views, because they are a frozen contract and one home for them is the only way to keep them frozen. The card API returns five mutually incompatible `409`/`403` shapes — `wip_limit_exceeded` and `weight_limit_exceeded` carry no `detail` key at all, `wip_hard_blocked` carries both `detail` and `code`, and the move assignee gate is the only `403` in the card API with a `code`. The web client reads those field names directly, so converging the shapes needs a major version bump. `backend/boards/tests/test_card_error_bodies.py` pins every one by exact dictionary equality.

The adapter does **not** wrap these in a DRF `APIException`. DRF coerces every value in an exception detail to a string, which would turn `current_count`, `wip_limit`, `card_weight`, and `current_version` into strings and break clients that compare them numerically.

`boards/services/errors.py` is **not** an extension point and carries no stability guarantee — unlike `boards/hooks.py`. The hierarchy is expected to change when the error bodies are converged.

## Roles

`boards/permissions.py` exposes two resolvers over one shared precedence ladder:

| Function | Use |
|---|---|
| `get_board_role(user, board)` | one board |
| `get_board_roles(user, boards)` | a list of boards, in a fixed two queries |

Resolving a role per board is an N+1 on any board that derives its role from a group, which is why the bulk form exists — and why re-implementing the ladder to dodge that N+1 is what produced the MCP fork. Both resolvers now delegate to the same private helpers; only the way they *load* memberships differs. Boards passed to `get_board_roles` must be loaded with `GROUP_ANCESTOR_SELECT_RELATED` applied, or the ancestor walk reintroduces the N+1 one level down.

`can_modify_others_content()` — the ownership gate — also lives in `permissions.py` rather than in the views package, so a service can call it without importing from `boards.views`.

### The `role` parameter fails closed

Every service function takes an optional `role`, so an adapter that has just resolved the role — `get_board_for_user()` does, as part of its own access check — does not pay for it twice. On a group-inherited board that second resolution is a real query.

A parameter that carries authorization state is only safe if a wrong value cannot be believed, so both resolvers leave a memo on the board instance recording which role they resolved and for whom, and the service accepts a supplied role only when it matches that memo. Anything else is discarded, logged, and the role is derived from the database instead. Two mistakes are therefore impossible rather than merely discouraged: passing `"admin"` outright, and — the likelier one, now that `get_board_roles` returns a `{board_id: role}` dict — indexing that dict with the wrong board id. Both just cost the query the parameter existed to save.

The memo is set by the resolvers alone and is never an input. A caller with no already-resolved role passes `None`, which is always correct.

## Write paths that remain divergent

Two paths deliberately do **not** go through the card service. Both are documented divergences, not oversights. (The operator seed commands — `seed_demo_data`, including `--demo-site`, `seed_template_boards`, and `benchmark` — also write cards directly with `Card.objects.create`/`bulk_create` and are exempt from WIP and weight limits for the same reason as import: they build a board as designed, which may be over its limits. They are management commands, not an API write path.)

**Import / export** (`boards/views/import_export.py`) creates cards with `bulk_create` into a board it has just created. It does not enforce WIP or weight limits — by design, since an import restores a board as exported and the sample boards each ship one over-WIP column (#1428) — does not compact positions, writes one `board.created` broadcast instead of per-card events, and fires no card mutation hooks. Calling a per-card service in a loop would mean O(n) round trips and a row lock per card on a 500-card import. There is a second reason to leave it alone: `bulk_create` does not emit `post_save`, so importing movement history does not notify assignees — routing import through a service that creates `CardMovement` rows individually would send a notification per imported movement.

**Django admin** (`boards/admin.py`, `CardAdmin.save_model`) broadcasts card events but skips the version bump, the `CardMovement` audit trail, the board-level RBAC check, and the hooks. An admin moving a card between columns therefore leaves no audit trail. WIP and weight limits and `allow_card_creation` *are* applied since 1.2: `CardAdminForm.clean()` calls the service's own `enforce_column_limits()` and reports a refusal as a form error, with no `force` override (#1428). Routing the rest through the service is still the strongest candidate to migrate next — it is a single call site.

## A service that is not a transition: `custom_fields`

`boards/services/custom_fields.py` (#371) is the second module in the package and does not
follow the `cards.py` shape, deliberately. It owns no transaction, no role check and no
broadcast — writing a card's custom field values is not a transition of its own, it is part
of the card update that contains it.

The split it does own is the one worth keeping: validation and per-type casting stay at the
serializer boundary (`CustomFieldValuesField`), while the **diff** — deciding which
submitted values actually changed — and the `custom_field_value_changed` signal fan-out
live in the service. That is what keeps a client echoing back the representation it was
given from firing an enterprise audit-log entry for a change nobody made.

It is called from `CardSerializer.create`/`update`, which run inside `update_card`'s and
`create_card`'s transaction, so the values roll back with the card and the deferred
`card.updated` broadcast already reflects them.

## Adding to this layer

Swimlane and column reorder and the other structural mutations are slated to follow in this package, which is why `boards/services/` is a package rather than a single module. When adding a transition:

1. Put the invariants in a service function; leave parsing, validation, and rendering to the caller.
2. Add a class to `errors.py` for each new failure mode — never build a response body in a view.
3. Reach `broadcast` and `hooks` through the **module object** (`from .. import broadcast as _broadcast`). The test suite patches `boards.broadcast.broadcast_board_event` at its source module, and a direct-name import binds a reference the patch cannot reach — so tests that patch only to suppress the channel layer would silently start broadcasting for real.
4. Register hook callbacks by reading `hooks.CARD_MUTATION_HOOKS` inside the `on_commit` callback. Enterprise code appends to that list in place; a copy taken at import time would miss late registrations, and rebinding the attribute would drop every enterprise handler. Each handler runs in isolation (`_run_hooks`): an exception is logged (handler name, ids, event type, exception class only) and swallowed, because the write is already committed and a 500 would invite a duplicate-creating retry. Handlers must therefore handle their own failures; they cannot veto or roll back the write.
5. Add a query budget to `CardMutationQueryCountTests`. Mutation budgets are `measured + 3`, tighter than the 2× used for read endpoints, because they have to catch a constant regression rather than a row-scaling one.

## Frozen asymmetries

Three things in this layer look like bugs and are contract. Do not "fix" them without a major version bump:

- `unarchive` broadcasts the WebSocket event `card.unarchived` but fires the hook event `card.restored`. Both names are independently frozen.
- `card.archived` broadcasts only `{"card_uid": ...}` while `card.unarchived` broadcasts the whole card. A client only needs to drop an archived card from its view.
- `update_card` and `delete_card` reject an archived card; `move_card` accepts one. The move endpoint has always read through the unfiltered manager, so archiving never froze a card's position — a restored card returns to wherever it was put.
- The error bodies described above.
