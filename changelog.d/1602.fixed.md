Deleting a column, swimlane, or board, through the API or the Django admin, while someone was creating a card in it or moving a card into it could fail with a server error on PostgreSQL. The delete now waits for the in-progress card and removes it along with the rest. A card create or move (including one made in the Django admin) that arrives while the delete is running now waits for it and is refused cleanly — `404` from the API, a form error in the admin — instead of failing with a server error. Deleting a board while its columns or swimlanes were being reordered could also fail with a server error; the two now wait for each other. Requests that change a board, column, or swimlane (board settings, share link, move to a group, column and swimlane edits, custom-field definitions, labels, members, invites, and the corresponding admin pages) that arrive while it is being deleted now wait and answer `404` without writing anything; previously some of them could fail with a server error or bring a just-deleted board back. The demo seed commands' `--wipe` now deletes boards the same way. In the rare case that cards keep arriving throughout a delete, the API answers `409 Conflict` (the admin shows an error) and deletes nothing, so the request can be retried. A board settings update that waited behind a share link change or a move to a group now applies only the fields it sent, a second move to a group now notifies the group the board actually left, and a custom-field definition or label edit that waited behind its deletion no longer brings the deleted item back. Creating a label or saved filter, or starring a board, while the board is being deleted now answers `404`; deleting a column, swimlane, or board that is already being deleted answers `404` instead of repeating the deletion event; and editing a column, swimlane, label, custom-field definition, or a board in the Django admin no longer overwrites a field another request changed while it waited.
